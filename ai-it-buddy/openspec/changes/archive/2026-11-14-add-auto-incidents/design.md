# Design

## Context

incident-radar уже умеет считать долю 5xx за окно `since/until` и отдает отчет по JSON Schema через MCP с Bearer-токеном. Ядро уже умеет объявлять инциденты и рассылать уведомления (ручной путь SRE).

## Goals / Non-Goals

**Goals:**
- Инцидент в чате раньше первой жалобы, без участия человека.
- Никаких ложных тревог от одиночного всплеска и никакого мигания открыт-закрыт.

**Non-Goals:**
- Свой парсер логов в ядре: считает радар, ядро только принимает решение.
- Корреляция причин и автоматическое восстановление.

## Decisions

- Ядро вызывает радар как обычный MCP-клиент (тот же протокол, что у агентов), а не читает файлы: радар остается единственным местом, где проверяются пути, лимиты и формат.
- Гистерезис: открыть при доле 5xx >= 20% две проверки подряд и не меньше 20 запросов в окне; закрыть при < 5% три проверки подряд; между порогами состояние не меняется. Окно 30 секунд, интервал 10 секунд: инцидент через ~20-30 секунд после начала сбоя.
- Радар закрывает только свои инциденты (`by = incident-radar`). Решение человека важнее автоматики.
- Радар недоступен - ничего не открываем и не закрываем, метрика `result=error` и алерт `RadarUnavailable`. Сессия MCP пересоздается после ошибки.
- Сбой в демо - через генератор логов с долей 5xx на основных путях сервиса, а не через ручку ядра: проверяется весь путь лог -> радар -> ядро -> уведомление.

## Risks / Trade-offs

- [Радар читает весь файл на каждый вызов] -> ротация в loggen (20 МБ), окно по времени отбрасывает старые строки; для продакшена - чтение по смещению или Loki.
- [Состояние гистерезиса в памяти] -> после перезапуска ядра счет проверок начинается заново, инцидент в базе сохраняется.
