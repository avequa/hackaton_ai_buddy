# Design

## Context

Все операции ядра - короткие изменения под одним mutex, ответы нужны быстро (агент вызывает инструменты в цикле). Объем данных маленький: десятки сотрудников, сотни заявок.

## Goals / Non-Goals

**Goals:**
- Ничего не терять при штатном перезапуске; при падении теряется не больше секунды изменений.
- Падение базы не останавливает помощника.

**Non-Goals:**
- Несколько экземпляров ядра одновременно (нужна была бы запись через базу на каждой операции).
- Хранение текста переписки: в базу попадают только счетчики тем.

## Decisions

- Write-behind вместо записи на каждой операции. Рабочая копия в памяти помечает измененные объекты (dirty set); `TakeChanges` забирает копии под коротким mutex, запись идет без блокировки ядра. Неудачная пачка возвращается в dirty set и уйдет со следующей. Альтернатива - транзакция на каждую операцию - проще в рассуждениях, но привязывает время ответа к базе и роняет помощника вместе с ней.
- Upsert по ключу для изменяемых объектов, только вставка для журналов (выдачи, события безопасности). Повтор пачки идемпотентен.
- Заявка хранится как jsonb плюс колонки для фильтров: модель заявки меняется чаще схемы.
- Миграции встроены в бинарник (`embed`), применяются под advisory lock.
- Время из базы читается в UTC: иначе после перезапуска даты в API меняли бы часовой пояс.
- Поиск: `tsvector` с весами (заголовок и теги выше текста), запрос строится из основ слов с префиксным поиском и объединением через ИЛИ, жаргон (впн, гит, тормозит) раскрывается словарем до поиска - одинаково для Postgres и памяти.

## Risks / Trade-offs

- [Падение процесса теряет до секунды изменений] -> интервал записи 1 секунда, финальная запись при SIGTERM.
- [Долгая недоступность базы растит память] -> метрика `buddy_store_pending_changes` и алерт `PostgresWritesFailing`.
