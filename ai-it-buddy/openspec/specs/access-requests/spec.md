# access-requests Specification

## Purpose
Заявки на доступ к корпоративным сервисам: агент готовит черновик, сервер проверяет права и политику роли, человек подтверждает, согласующий решает.

## Requirements

### Requirement: Черновик создает сервер с проверками
Инструмент `draft_access_request` SHALL создавать заявку только в статусе `draft`. Сервер MUST проверять существование сервиса, проекта и уровня, обязательное обоснование, уже выданный доступ и незакрытую заявку на тот же проект.

#### Scenario: Доступ уже есть
- **WHEN** у Анны есть `write` к проекту Grafana и агент просит `read`
- **THEN** результат `already_granted` с текущим уровнем, новая заявка не создается

#### Scenario: Нет обоснования
- **WHEN** обоснование пустое
- **THEN** инструмент возвращает ошибку `invalid` с подсказкой, что нужно указать задачу

### Requirement: Подтверждает только человек
Перевод черновика дальше по процессу SHALL выполняться только через `POST /api/requests/{id}/confirm` с токеном интерфейса владельца заявки. У агента MUST не быть инструмента подтверждения.

#### Scenario: Чужая заявка
- **WHEN** Павел подтверждает черновик Анны
- **THEN** ответ 404 (как будто заявки нет), а попытка записывается как событие безопасности `foreign_object`

### Requirement: Политика роли
Сервер SHALL помечать черновик `needs_mentor`, если уровень доступа нетипичен для роли или проект принадлежит другой команде. После подтверждения такая заявка MUST уходить наставнику (`pending_mentor`), а не согласующему.

#### Scenario: Доступ к проекту другой команды
- **WHEN** стажер команды payments подтверждает заявку на проект команды cabinet
- **THEN** заявка переходит в `pending_mentor`, наставник получает уведомление с причинами

#### Scenario: Наставник одобряет
- **WHEN** наставник одобряет заявку из своей очереди
- **THEN** заявка переходит в `in_review` у согласующего по уровню (владелец проекта, руководитель или DevOps)

### Requirement: Согласование
Уровень `read` с согласующим `auto` SHALL выдаваться сразу при подтверждении. Остальные заявки MUST решаться согласующим через заданную задержку. Стажеру MUST не выдаваться `admin` и доступ к `k8s-prod`: отказ содержит причину и что сделать вместо этого.

#### Scenario: Стажер просит admin
- **WHEN** заявка стажера на `admin` доходит до решения DevOps
- **THEN** статус `rejected`, в причине предложено оформить `write`

### Requirement: Стартовый набор одной кнопкой
При первом входе стажера система SHALL предложить стартовый набор доступов (VPN, GitLab, Jira, Confluence его команды). `POST /api/onboarding/starter-pack` MUST создавать черновики только для недостающих доступов, `POST /api/requests/confirm-batch` MUST подтверждать их одной операцией с результатом по каждой заявке.

#### Scenario: Часть доступов уже есть
- **WHEN** у стажера уже есть VPN и Confluence
- **THEN** набор содержит `already_granted` для них и черновики для GitLab и Jira
