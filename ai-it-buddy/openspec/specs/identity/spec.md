# identity Specification

## Purpose
Кто действует в системе: пользователь интерфейса или агент от его имени. Личность всегда берется из подписанного токена, а не из текста запроса или аргументов модели.

## Requirements

### Requirement: Вход под демо-персоной
Система SHALL выдавать токен интерфейса (JWT HS256, audience `ui`, срок 12 часов) по `POST /api/auth/login` для сотрудника из справочника. Неизвестный сотрудник MUST получать 404.

#### Scenario: Стажер входит
- **WHEN** интерфейс вызывает `POST /api/auth/login` с `{"user_id": "anna.intern"}`
- **THEN** ответ содержит токен и профиль Анны (роль, команда, наставник)

#### Scenario: Неизвестный сотрудник
- **WHEN** вход выполняется с `user_id`, которого нет в справочнике
- **THEN** ответ 404, токен не выдается

### Requirement: Отдельный короткий токен агента
Для каждого хода диалога ядро SHALL выпускать агенту токен с audience `mcp` и сроком 5 минут. MCP-серверы MUST принимать только его, HTTP API интерфейса MUST не принимать его.

#### Scenario: Агент пытается вызвать API интерфейса
- **WHEN** запрос к `/api/requests/{id}/confirm` приходит с токеном audience `mcp`
- **THEN** ответ 401, заявка не подтверждается

### Requirement: Пользователь инструмента - из токена
MCP-инструменты SHALL определять пользователя только по токену запроса. Аргументы инструментов MUST не содержать идентификатор пользователя.

#### Scenario: Модель пытается действовать за другого
- **WHEN** агент, работающий с токеном Анны, вызывает `get_my_requests`
- **THEN** возвращаются только заявки Анны, независимо от текста сообщения
