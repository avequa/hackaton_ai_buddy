# AI IT-Buddy

Помощник стажера в первые недели: доступы, техподдержка, оборудование, путь адаптации.
Hack&Change 2026, кейс Авито. Данные синтетические, инструкции в `data/kb` тестовые и не являются регламентами Авито.

## Архитектура

```
UI ──► core (Go) ──► agent (Python, LangGraph) ──► llm-gateway (Go) ──► LLM
       ▲ │ │  ▲              │
       │ │ │  └── MCP + JWT ─┘
       │ │ └──► Postgres          состояние, база знаний (FTS, русская морфология)
       │ └────► incident-radar ◄── loggen (логи NGINX: VPN, GitLab)
       │          MCP, раз в 10 с
  Prometheus ◄── /metrics (core, llm-gateway) ──► Grafana, алерты
```

- `core` - HTTP API для интерфейса и четыре MCP-сервера: `/mcp/access`, `/mcp/helpdesk`, `/mcp/inventory`, `/mcp/onboarding`.
  Права, заявки, статусы и согласования живут здесь.
- `agent` - LangGraph: модель выбирает инструмент, ядро его выполняет. Сам агент ничего не меняет.
- `llm-gateway` - агент просит роль (`main`, `small`, `validator`), шлюз выбирает модель и переключается на запасную.

- `incident-radar` - разбор access-логов NGINX. Ядро спрашивает его по MCP о последних 30 секундах лога каждого сервиса
  и само открывает и закрывает инциденты.
- `Postgres` - заявки, доступы, склад, уведомления, события безопасности, база знаний.

Права проверяет сервер. Пользователь в MCP берется из JWT, а не из аргументов модели.
Агент получает токен с аудиторией `mcp` на 5 минут: им можно создать черновик, но нельзя подтвердить заявку.
Подтверждает человек в интерфейсе токеном сессии (`ui`). Запросы не по роли не блокируются: стажер видит причины,
а заявка сначала уходит наставнику.

## LLM

По умолчанию OpenRouter, бесплатные модели:

- `main`, `small`: `nvidia/nemotron-3.5-super-vl:free`
- `validator` и запасная: `thinkingmachines/inkling-small:free`

Ключ: https://openrouter.ai/settings/keys, переменная `OPENROUTER_API_KEY` в `.env`. Лимит: 50 запросов в день на аккаунт.

Другой провайдер (любой OpenAI-совместимый): правится `deploy/llm-gateway.yaml`, блоки `upstreams` и `targets`.
DeepSeek уже настроен: в `.env` строки `LLM_CONFIG=llm-gateway.deepseek.yaml` и `DEEPSEEK_API_KEY=...`.

## Запуск

Docker. Команды выполняются из папки `ai-it-buddy`, шлюз собирается из соседней `llm-gateway`.

```bash
cp .env.example .env          # вписать OPENROUTER_API_KEY
docker compose up -d --build
curl 127.0.0.1:8080/healthz
python3 scripts/check_llm.py  # 3 запроса к LLM
python3 scripts/demo.py       # все сценарии, около 10 запросов к LLM
```

| | |
|---|---|
| API | http://127.0.0.1:8080/api, спецификация: `/api/openapi.yaml` |
| Grafana | http://127.0.0.1:3001, дашборд AgentOps открывается на главной |
| Prometheus | http://127.0.0.1:9091, алерты: `/alerts` |
| LLM-шлюз | http://127.0.0.1:4001 |
| loggen | http://127.0.0.1:8092/outages - включить сбой для демо |

## Сценарии

1. Доступ по описанию задачи. «Нужно поправить алерт» -> Grafana, проект своей команды, уровень write -> черновик ->
   подтверждение -> согласует владелец проекта -> шаг адаптации «доступ к Grafana» закрывается сам.
2. Не по роли. Стажер просит прод -> причины и совет обсудить с наставником -> очередь наставника -> отказ с причиной.
3. Инцидент. VPN лежит -> «проблема не у тебя», тикет не создается: сервер не дает завести дубликат.
4. Оборудование. Позиции нет -> альтернативы из наличия, лист ожидания, закупка только в пределах нормы роли.
5. Путь адаптации. Шаги по неделям, у каждого свой способ подтверждения: сам, наставник, руководитель, система.
6. Сбой от SRE. Дежурный объявляет сбой -> всем сразу приходит уведомление в окно чата -> помощник отвечает
   «это не у тебя», тикет не создается -> SRE закрывает сбой, всем приходит «восстановлено».
7. Стартовый набор. При первом входе стажеру предлагается пакет заявок на VPN, GitLab, Jira и Confluence своей
   команды, подтверждается одной кнопкой.
8. Сводка для наставника. Перед встречей 1:1: что сделано, где отстает, что ждет его решения, с какими темами
   стажер приходил к помощнику (без текста переписки), готовый список того, что обсудить. Раз в неделю приходит
   уведомлением (`DIGEST_INTERVAL`, по умолчанию 168h).
9. Тревоги. Попытка открыть чужую заявку, действие не по роли, попытка уговорить помощника обойти правила
   («игнорируй инструкции», «я теперь наставник», вопросы про другого стажера) -> наставник и руководитель получают
   уведомление. Действия при этом уже заблокированы сервером, это сигнал людям.
10. Сбой по логам. VPN начинает отвечать 5xx -> incident-radar видит рост ошибок в логах NGINX -> через 20-30 секунд
   ядро само открывает инцидент и пишет всем в чат -> ошибки ушли -> через ~40 секунд закрывает. Объявленный человеком
   сбой радар не трогает. `python3 scripts/demo.py radar`.
11. Перезапуск. Заявки и уведомления на месте после `docker compose restart core`. `python3 scripts/demo.py restart`.

Сбой для демо:

```bash
curl -X POST 127.0.0.1:8092/outages -d '{"service":"vpn","error_rate":0.7}'   # через логи, как в жизни
curl -X POST 127.0.0.1:8080/api/demo/incidents -H 'X-Demo-Token: demo' \
  -d '{"service":"vpn","title":"Недоступен шлюз VPN","active":true}'          # сразу, без логов
```

## Надежность

- Ядро отвечает из памяти, изменения раз в секунду уходят в Postgres одной транзакцией. База недоступна - ядро
  работает дальше, изменения копятся и записываются, когда она вернется. `/readyz` показывает `degraded` и сколько
  изменений ждут записи. При остановке - финальная запись.
- Поиск по базе знаний при ошибке Postgres идет в памяти.
- Радар недоступен - инциденты не открываются и не закрываются автоматически, ручной путь SRE работает.
- Агент недоступен или кончился лимит модели - пользователь получает понятное сообщение, заявки и уведомления работают.
- Алерты (`deploy/prometheus/alerts.yml`, тесты `alerts_test.yml`): ядро недоступно, ошибки записи в Postgres,
  радар не отвечает, доля 5xx сервиса выше 20%, ошибки чата, 429 от провайдера модели, атаки через чат.

## Метрики

Дашборд AgentOps в Grafana:

- доля вопросов, закрытых без наставника;
- конверсия черновик -> подтверждение;
- сколько раз помощник не дал завести тикет во время инцидента;
- попытки выйти за права по видам;
- объявленные инциденты;
- доля 5xx по логам сервисов и проверки радара;
- изменения, ждущие записи в Postgres, и время с последней записи;
- доля заявок не по роли;
- токены на ход диалога;
- переключения на запасную модель;
- p95 ответа.

Счетчики ядра начинаются с `buddy_`, шлюза - с `llm_gateway_`.

## Тесты

```bash
scripts/coverage.sh                                     # все модули, Postgres для тестов поднимется в Docker
cd core && TEST_DATABASE_URL=... go test -race -p 1 -cover ./...    # 92%
cd agent && pip install -r requirements-dev.txt && pytest --cov=buddy_agent   # 99%
```

Тесты агента не ходят в LLM, модель заменена скриптом. Тесты хранилища идут на настоящем Postgres.

## Где что

- `core/internal/domain` - заявки, политика, склад, база знаний, адаптация
- `core/internal/mcpapi` - инструменты для агента
- `core/internal/httpapi` - API для интерфейса, `openapi.yaml`
- `core/internal/authn` - имитация IdP (JWT)
- `core/internal/store` - Postgres: миграции, запись изменений, полнотекстовый поиск
- `core/internal/radar` - клиент incident-radar и правила открытия и закрытия инцидентов
- `loggen` - генератор логов NGINX с включаемым сбоем
- `openspec` - спецификации поведения и архив изменений
- `agent/buddy_agent` - граф, промпт, HTTP-вход агента
- `data/seed` - сотрудники, каталог сервисов, роли, склад, шаги адаптации
- `data/kb` - база знаний
- `deploy` - конфиги шлюза, Prometheus, Grafana
- `docs/api.md` - API для фронтенда

## Ограничения прототипа

- Ядро - один экземпляр: рабочая копия состояния в памяти, база - для сохранности. Для нескольких экземпляров
  нужна запись через базу на каждой операции.
- История диалогов хранится в памяти агента. Поэтому агент запускается одним процессом.
- Логи сервисов синтетические (loggen). Радар читает файл целиком на каждую проверку: для продакшена - чтение по
  смещению или Loki.
